## 0. 结论先行

| 问题 | 结论 |
|---|---|
| 用 minimind-o 做 base 合适吗 | **合适，但定位要准**：它是可解剖的实验台，不是机器人语音的产品基座 |
| 为什么不直接用 Qwen 生态 | 不是「太大」，而是**不给你改结构的机会**。Qwen3-Omni 是 30B-A3B（Apache 2.0），Orin NX 跑不动；3B 版能跑，但只能当黑盒 |
| Qwen 的正确用法 | **上限参照 + 数据/设计来源**。minimind-o 的训练语音就是 Qwen3-TTS 合成的，Thinker–Talker 结构也继承自 Qwen2.5/3-Omni |
| 要补的核心知识 | **语言建模与 Transformer 基础**，以及数据配比、loss、推理状态和跨模态对齐；先读第 0 课，再逐项实验 |
| 算力分工 | 个人机做推理与走读，训练用自备服务器（mini 全链 3090 级约 2h） |
| 怎么接回现有工程 | **音频平面不进 ROS**；omni 做成与 ASR/TTS 平级的 `ConversationEngine`，ROS 只承载控制与事件（ADR-004） |
| 能否扩到动作策略 | 结构上可以（一个主干两个 decoder），能力上分三层；真操作别用这个基座（ADR-005） |

## 1. 为什么是 minimind-o（证据，不是感觉）

| 维度 | 事实 | 对学习者意味着什么 |
|---|---|---|
| 可训练参数 | 113.13M（dense）/ 314.89M-A115M（MoE） | 单卡可训，能反复做消融 |
| 运行时总参数 | 537.83M（含冻结的 SenseVoice 234M + Mimi 96M + SigLIP 95M） | **能落到 Orin NX**，demo 可做到真机 |
| 代码量 | `model_minimind.py` 292 行 + `model_omni.py` 461 行 + 训练 255 行 + 推理 244 行 | 一天能读完，能改到骨头 |
| 训练成本 | mini 数据集单卡 3090 约 2 小时跑通 Thinker–Talker 全链 | 学习闭环和工程闭环能合并 |
| 输入接口 | 16k fbank（SenseVoice） | ASR 前端，你的主场 |
| 输出接口 | 12.5 Hz × 8 层 Mimi codes，24 kHz | 码本 + 声码器，你的主场 |

对比 Qwen 生态：

| 模型 | 规模 | 能否改结构 | 能否上 Orin NX |
|---|---|---|---|
| Qwen3-Omni-30B-A3B | 30B total / 3B active | 难（MoE + 多模态工程栈） | 否 |
| Qwen2.5-Omni-3B | 3B | 难 | 勉强（int4 量化后） |
| Qwen3-ASR / Qwen3-TTS | 各自独立 | 只能换，不能改 | 分别可行 |
| **minimind-3o** | **113M + 425M 冻结** | **可以改到每一行** | **是** |

> 注意：`qwen-asr + qwen-tts + live-harness` 那套本质**仍然是级联**，只是把 ASR/TTS 换成了更强的模型。它解决不了「隐藏层直连」和「双工时序」这两个真问题。

## 2. 三个必须先认清的边界

### 2.1 它不是真双工，是「VAD 门控的半双工 + 打断」

三个证据都在代码里：

1. `webui/web_demo.py` 的 `RealtimeSession`：silero VAD，阈值 0.8，`min_silence_ms=800`。打断判定 = 「VAD 说有人在说话」。
2. `model_omni.py::encode_audio_inputs()`：整段 fbank 一次性送进 SenseVoice，**输入侧没有流式**。
3. `model_omni.py::forward()`：输入音频只在 `start_pos == 0` 时注入；生成期间没有持续把新麦克风音频加入当前模型状态。文本与音频并行输出本身不能证明全双工。

### 2.2 码率算术：文本位置、音频帧与生成耗时要分开

```text
Mimi: 12.5 帧/秒，每帧 8 个码本索引
音频时长 ≈ 有效音频帧数 / 12.5
有效音频帧数不必等于有效文本 token 数
```

训练中音频目标按自身长度填充；推理中，文本 EOS 后仍可继续生成音频，直到音频停止条件满足。共用生成位置与延迟码本排列，不足以推出“语音时长被文本 token 数锁死”或“模型没有 duration 自由度”。

当前词表为 6400 的 byte-level BPE，字节可以被合并。“你好”和“机器人”在当前 tokenizer 中各为一个 token，不能从中文 UTF-8 字节数推导每字 token 数，更不能据此断言中文应为 4 字/秒。

后续测量分别记录文本 token 数、有效音频帧数、文本/音频结束时刻和实际解码时长。`chars_per_sec` 是描述性指标，不是对某个固定语速推导的验证。基础解释见[第 0 课](第_0_课：LLM基础_从音频工程到语言模型.md)。

### 2.3 它不是「大脑」

0.1B 主干，工具调用、多轮指代、领域知识都撑不住。在机器人上它的价值在**语音层**（听、判端点、接话、渲染语音），不在语义层。

### 2.4 中文能力来自 full 权重，不是 mini 训练

README 明说 mini 只筛了英文，中文 Talker 的难度远高于「单卡 2 小时」。所以：**用发布权重做中文 demo，不要试图从零训中文 Omni。**

## 3. 架构决策记录（ADR）

> 这一节记录三个关键判断。后续课程如果推翻其中任何一条，在这里改，不要散落在各课里。

### ADR-001：System-1 不该由 minimind-o 来做

**背景**：上一轮把 minimind-o 放在「System-1 / System-2」双过程架构的 System-1 位置，容易和 VLA 领域的同名概念混淆。

**三个同名概念，必须先拆开**：

| 语境 | System-2（慢） | System-1（快） | System-1 的输出 |
|---|---|---|---|
| 机器人 VLA（GR00T / Helix / π0） | VLM 慢规划 | diffusion / flow 动作策略 | 关节或末端**动作序列** |
| 对话双过程（Kahneman） | LLM 语义推理 | 端点、接话、打断的**反射** | 状态切换 + 短语音 |
| 级联语音 | 大 LLM | 小 ASR / NLU | 文本 |

**结论**：minimind-o **两者都不是**。它没有动作输出、没有本体感知、没有高频控制回路，因此不是 VLA 的 System-1；它的 Thinker 也只是个 0.1B 文本 LM，做不了可靠的语义判断。**它的正确定位是「耳朵 + 嘴」——语音 I/O 层。**

**判断层应该拆成两级**：

| 层级 | 判什么 | 用什么 | 延迟预算 |
|---|---|---|---|
| 声学反射 | 有没有人说话、说完了没有、是不是对我说的（DOA） | VAD + **turn-end predictor**（CRNN/Conformer，10M 级） | 20–50 ms |
| 语义反射 | 这半句话是不是在打断我 / 要不要接话 | 0.5–1.5B audio-LLM，或大模型的 speculative 判定 | 150–400 ms |

现有 `speech_core` 已经有 VAD/KWS（见《智能语音》第 3、10 课），**缺的是 turn-end predictor**。这是最便宜的增量，也是第 9 课的内容。

**为什么 Decision Transformer / JEPA 不合适**：它们是 `state → action` 的策略模型或世界模型；而 turn-taking 是 `P(turn end | audio history)` 的**序列分类**问题。用 DT 做端点检测既没有优势，也拿不到它依赖的 reward / 动力学结构。

### ADR-002：视觉通路撑不起 BEV + 云台相机

**事实**：

- 视觉编码器是 **SigLIP2 base-p32-256**，输入 256×256，输出 **8×8 = 64 个 token**，每个 token 覆盖 32×32 px。
- 视觉只在 I2T 阶段训练，且 `--mode vision_proj` 只更新 projector，编码器始终冻结。
- README 自评跨模型 I2V CER **0.8241**（Mini-Omni2 是 0.7609），即「勉强能描述，谈不上理解」。

**对 BEV 意味着什么**：一张 20m×20m 的 BEV 图压到 256×256，每个 token 对应 **2.5m×2.5m**。这个粒度做不了避障级推理。云台相机同理：单帧、无 ego-motion、无 3D 结构。

**结论**：**不要把机器人感知建在这条路上**。两个可选的有限用法：

1. **BEV 当示意图**：把 BEV 渲染成 256×256 的 RGB 卡片（自车、障碍、目标、可通行区用色块 + 图例），喂给模型当"看板"。只能回答粗粒度问题（"左边有障碍吗"），且需要几百条 SFT 数据教它读这张图。
2. **换编码器 + 重训 projector**：SigLIP2-so400m @384 + 2×2 tiling（256 token），或直接注入 BEVFormer/BEVDet 的 64 个 query。要改 `image_hidden_size`、`MMVisionProjector` 和 I2T 训练，属于「改造」而非「开箱」。

> 如果团队真的要图像理解：走 Qwen2.5-VL / 专用 VLM，别用 0.1B omni。这条通路的 demo 价值是「多模态演示」，不是「机器人视觉」。

### ADR-003：可以扩，但值得扩的不是 0.1B 本身

**结构上能不能扩**：能。Thinker 是标准 MiniMind transformer（8 层 / 768 hidden / GQA / SwiGLU / RoPE，vocab 6400），Talker 是 4 层独立 block，二者通过 `bridge_layer` 的隐状态 + `embed_proj` 解耦——这个接口很干净。

**扩展需要评估三类变化**：

1. **参数与接口变化**：加宽、加深或替换主干后，哪些权重能够继承、哪些需要重新初始化或适配，要具体设计，不能直接保证能力保持。
2. **序列变化**：新 tokenizer、chat template、特殊 token 和位置编码会改变条件序列；同一段文本的 token 数也可能变化。
3. **表征变化**：相同 hidden size 不等于相同语义空间。Talker 与音频 projector 对新 Thinker 的适配，需要训练数据和验证集。

**可选研究方向：Thinker swap**——探索用更强的预训练语言模型替换 Thinker，并评估现有 Talker、Mimi 与 projector 能复用到什么程度；目前不预设它是最优路径。

- `bridge_layer` 与 `embed_proj` 提供连接位置，但还需处理缓存、停止条件和表示分布等差异。
- 冻结 Thinker、训练适配模块可以作为起点；训练时间和质量需要按数据量、序列长度及实测吞吐估计，暂无“4090 一两天”的保证。
- tokenizer 会影响序列效率与对齐学习，但不能直接由 token 数推出发音时长。是否需要改变音频调度，应由新方案的训练与生成表现决定。

**结论**：minimind-o 值得作为**实验基座**（改 Talker、改双工、改码本），不值得作为**能力基座**（拼知识、拼推理）。第 13 课做这个 swap。

### ADR-004：集成到现有工程——音频平面不进 ROS

**背景**：两种集成都成立——(a) 以 omni runtime 为进程主体，外面包一层轻量 ROS facade；(b) 以 `speech_core` 为主体，把 omni 当 `third_party`。选哪条不是关键，关键是有四条不能破的约束。

**结论**：**PCM 永不跨 ROS；ROS 只承载控制与事件**。omni 应做成与 `AsrEngine` / `TtsEngine` **平级**的 `ConversationEngine`，而不是某个 engine 的 backend——它有独立状态机（listening / thinking / speaking / interrupted）和双向流，不是"一段进一段出"的同步接口。

| 约束 | 原因 | 做法 |
|---|---|---|
| PCM 不进 DDS | 16k 单声道 10ms 帧 = 100 msg/s，序列化 + 调度抖动会毁掉 p95 | 音频图留在进程内（ring buffer / 共享内存），ROS 只发状态与转写 |
| 时钟只有一个 owner | 两个 10ms tick 必然漂移，AEC 参考对不齐 | 沿用 `AudioEngine` 的 tick，omni 推理循环挂在它下面，不自建时钟 |
| AEC 参考必须 sample-aligned | 双工模型会"听见自己"，参考错位会把回声学成语音 | omni 输出 PCM 回灌 `ApmPipeline` 的参考通道，与麦克风同一时间基 |
| 延迟预算在进程内闭环 | 多一跳 ROS 就多一份不可控 | facade 只发布 `speaking` / `interrupted` 等事件，不搬运数据 |

**真正的收益**：同一套 AEC / 波束 / GTCRN 前端同时喂串行链路与 omni，A/B 才是同一输入下的比较，而不是"干净录音 vs 机器人现场"的伪对比。

### ADR-005：能不能从「说」扩到「做」（flow / diffusion 动作策略）

**问题**：能否在 minimind-o 上继续扩展出 diffusion / flow 动作策略，直接输出关节或末端动作序列？

**结构上：可以，而且接口比想象中自然。** `bridge_states` 是 Thinker 的中层语义状态，Talker 只是它的一个 decoder；再加一个 ActionExpert 就是「一个主干、两个 decoder」。这正是 GR00T N1 / π0 的形状（VLM 主干 + flow-matching 动作专家）。

```
Thinker(第 3 层) ──┬─→ Talker ─→ 8 × Mimi codes @ 12.5 Hz
                   └─→ ActionExpert(4L, flow matching) ─→ action chunk (H × D)
proprio(关节/夹爪) → MLP → 1 个占位 token 注入 Thinker 序列（和 spk_emb 同一手法）
```

**能力上：三层必须分开看。**

| Tier | 做什么 | 可行性 | 周期 |
|---|---|---|---|
| 1 | 语音 → 结构化指令 → 现有 ROS action server | **马上可做**，不需要任何 VLA 训练 | 1–2 周 |
| 2 | 冻结 Thinker，加 flow-matching action expert，输出低频 waypoint / 玩具任务 | 研究 demo 可行；0.1B + 64 视觉 token 撑不起真操作 | 4–8 周 |
| 3 | 真正的 pixels→actions 操作策略 | **不要用这个基座**，用 GR00T N1 / π0 / OpenVLA | 月级 |

**四道硬约束**（Tier 2 会立刻撞上）：

1. **视觉分辨率**：64 个 token、每 token 32×32 px，做不了抓取级空间推理。Tier 2 只能做"桌面大物体 / 二维平面"任务。
2. **时间分辨率**：Talker 是 12.5 Hz，动作控制要 30–50 Hz。解法不是提高帧率，而是**输出动作块 + 下游控制器插值**（action chunking，π0 的做法）。
3. **没有本体感知**：要加 proprio encoder；数据管线从 Mimi codes 换成 LeRobot / 自有遥操作轨迹，评估从 CER 换成动作 L2 + sim rollout，是另一套节奏。
4. **梯度冲突**：语音与动作的数据率、损失尺度差一个量级。第一步必须**冻结 Thinker、只训 ActionExpert**，并监控语音 CER 不退化。

**结论**：Tier 1 是工程，Tier 2 是研究，Tier 3 是另一个产品。三者不要混在同一个里程碑里。第 14 课做 Tier 2 的最小验证。

## 6. 工程约定

1. **不动 upstream master**：`minimind-o` 保持在 `exp/*` 分支上改，`upstream` 保留用于拉作者的修复（该仓库仍在活跃修 bug）。
2. **所有实验必留痕**：每次跑 `bench/run_bench.py`，结果落 `bench/results/*.jsonl`，文件名带日期和 tag。
3. **延迟数字必须带设备**：CPU / 3090 / Orin NX 的数字不可混在一张表里比较。
4. **按学习目标控制训练规模**：第 0 课不要求训练；先理解并测量现有模型，再在基础课中做小规模纯文本训练练习，Omni 训练留到对应阶段。loss 下降不能代替任务基线对比。
5. **评估集先于模型**：`bench/cases/` 的用例数少于 30 条时，不允许下"效果提升"的结论。
